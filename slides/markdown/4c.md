## C1 · CONNEXIONS

**Objectif :** partir de ce que vous connaissez

- Classes, héritage, état mutable
- SOLID : SRP, OCP, LSP, ISP, DIP
- Python : classes, propriétés, `dataclass`
- Programmation fonctionnelle : les `lambda`, peut-être

## C2 · CONTEXTE

### De SOLID à CUPID

- 🔧 Une seule chose à faire → **U**nix
- 🏠 Des pièces qu'on remplace → **C**omposable
- 🗺️ Le vocabulaire du métier → **D**omain-based

--

## C2 · CONTEXTE

### CUPID : cinq propriétés du code

| Lettre | Question |
|:-:|---|
| **C** | Puis-je brancher ce morceau ailleurs ? |
| **U** | Fait-il une seule chose, bien ? |
| **P** | Fait-il ce qu'on attend, tout le temps ? |
| **I** | S'écrit-il comme on écrit en Python ? |
| **D** | Parle-t-il le langage du métier ? |

## C2 · CONTEXTE

### Le harnais

- Analyse statique du code, sans l'exécuter
- Chaque règle pose une question et attend un refactoring

- Se lance en local, ou dans la CI

## C2 · CONTEXTE : phase 2

### De l'objet au fonctionnel

- Héritage → **union** de dataclasses (ADT)
- État mutable → **données immuables**
- `if` et `try` → **`match`**
- Méthodes avec effets → **fonctions pures**

***Rendre les états illégaux impossibles***

### CUPID ou SOLID ?

**Question :** dans quel cas choisiriez-vous CUPID plutôt que SOLID ?

**À retenir :**

- SOLID : bon pour l'objet classique
- CUPID : bon pour un code plus fonctionnel
- CUTE : ce que le code apporte à l'équipe
- Make it CUTE !
